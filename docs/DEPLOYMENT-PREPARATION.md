## Priority-news template

Review `.github/workflow-templates/priority-news.yml` before separately approving its installation. It schedules at most once per hour (`17 * * * *`, UTC), uses a single concurrency group with no overlapping runs, and limits the complete job to ten minutes. It runs `tools/news-pipeline.py --run` with strict ingestion acknowledgement and visible failures. The job timeout can cancel a slow provider run before the runner's longer subprocess limits; cancellation is a failed update, not proof of a fresh feed. No history backfill or financial engine is invoked.

News delivery is exclusively authenticated Worker ingestion -> existing PRICES KV -> `/v1/news` and `/v1/globe` -> the website in worker mode. The scheduler never checks out or commits to the frontend, creates delivery PRs, triggers Pages builds, or deploys anything. Saved frontend articles remain a dated outage fallback; they do not need rebuilding for each API update. Configure the public production runtime with `dataMode=worker` and the approved Worker HTTPS base URL during a separately approved Pages release.

The scheduled producer has no Pixabay key and reuses its saved photo pool. It does not download or publish new photos. Before enabling, verify that the saved photo paths selected by the producer already exist in the deployed website. API JSON cannot publish a missing image file. New photo delivery needs a separately approved asset-hosting design; it must not be solved with automated frontend commits or Pages rebuilds. The old optional `--frontend` runner argument is a manual recovery/export facility, not the production delivery path, and is never used by this schedule.

At 744 hourly runs in a 31-day month, the worst-case ten-minute job limit is 7,440 minutes, exceeding the free 2,000-minute pool. Runner startup/post-job overhead, other workflows and retried runs also consume the private account's shared 2,000 free Actions minutes; this is not a guarantee of staying within that account-wide allowance. Review actual usage, alerts and a no-overage spending limit before enabling. Decrease cadence if measured usage needs more headroom. The template keeps contents permission read-only and saves bounded producer state in the private backend Actions cache; review retention/storage separately.

Secrets stay in provider/GitHub stores and are supplied only to the ingestion step. Generated logs and feeds must not be uploaded as unrestricted diagnostic artifacts. The pipeline's default preflight is safe without credentials; do not run `--run` during this preparation.
